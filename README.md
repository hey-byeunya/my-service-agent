# 이미 있어 — 이용 안내 챗봇 설계

## 이게 뭔가

**이미 있어**는 내가 가진 물건을 기록해 두고, 이미 있는 걸 까먹고 또 사는 일을 막아 주는 개인용 앱이다. 가진 물건은 "있템", 사고 싶은 건 "위시", 다 쓴 건 "쓴템" 세 칸에 나뉘어 담긴다.

이 저장소는 그 앱의 **이용 방법을 안내하는 챗봇을 어떻게 만들지 정한 설계 문서**다. 챗봇을 만들지는 않았다. 무엇을 맡기고 어디에서 멈추게 할지를 먼저 정해 문서로 남기는 것이 이번 과제다.

챗봇이 맡는 일은 안내다. "위시에 담아둔 걸 샀는데 어떻게 옮겨요?", "이 빨간 배지는 무슨 뜻이에요?", "카테고리는 꼭 넣어야 해요?" 같은 질문에 답한다.

**챗봇은 내 물건 정보를 직접 고치지 않는다.** 바꾸는 게 좋겠다고 제안하는 것까지만 하고, 실제로 바꾸는 건 사람이 앱 화면에서 직접 누른다.

## 설계 결정 요약

### 도구를 4개만 둔 이유

챗봇이 쓸 수 있는 기능을 네 개로 정했다. **사용법 문서에서 문장 찾기 / 내 물건이 몇 개인지 보기 / 내가 넣으려는 값이 규칙에 맞는지 봐주기 / 바꾸겠다고 제안하기.**

네 개로 나눈 기준은 "무엇을 돌려주는가"다. 첫 번째는 문장을, 두 번째는 개수를, 세 번째는 맞다·틀리다 판정을, 네 번째는 제안을 돌려준다. 그래서 같은 주제를 물어도 도구가 하나로 정해진다. "카테고리 꼭 넣어야 해요?"는 첫 번째, "안 넣으면 어떻게 돼요?"는 세 번째, "카테고리 없는 게 몇 개예요?"는 두 번째다.

다섯 번째를 넣어 보려니 하는 일이 이미 있는 도구와 겹쳤다. 도구가 많아 보이는 것보다, 어떤 질문이 어느 도구로 가는지가 헷갈리지 않는 게 중요하다고 봤다.

### 권한을 나눈 기준

**값을 보기만 하는 도구와 값을 바꾸는 도구로 나눴다.** 보기만 하는 게 셋, 바꾸는 게 하나다.

바꾸는 쪽 하나도 실제로는 바꾸지 않는다. 위시에 담아둔 물건을 있템으로 옮기는 일은 한 번 누르면 되돌릴 수 없고, 중간에 멈추는 일 없이 한 번에 끝난다. 게다가 옮기면서 수량이 무조건 1로 정해지는 딸린 효과도 있다. 이런 일을 챗봇이 알아서 하면 안 된다고 봐서, 챗봇은 "이렇게 바꿀까요?"라는 확인 카드를 띄우는 데까지만 하고, 확정은 사람이 앱 화면의 버튼을 눌러서 한다.

제안하는 쪽과 확정하는 쪽을 다른 곳에 둔 이유가 하나 더 있다. 챗봇이 제안하고 챗봇이 확정하면, 나중에 기록을 봐도 사용자가 정말 그걸 원했는지 알 수 없다.

그리고 **내 물건을 볼 때 "누구의 것을 볼지" 지정하는 칸을 아예 만들지 않았다.** 지금 로그인한 사람이 누구인지는 앱이 알고 있으니, 챗봇에게 물어볼 필요가 없다. 칸이 있으면 사용자가 쓴 문장이 그 칸을 채울 수 있고, 그러면 남의 것을 보라고 시킬 길이 생긴다.

### 실패했을 때 할 일을 그렇게 정한 근거

앞선 실습에서 배운 게 이 결정의 근거다.

도구 설명문에 **"모르면 추측하지 마"라고 적어 두는 것만으로는 막히지 않았다.** 챗봇은 추측을 멈추는 대신, 있지도 않은 창고 코드를 새로 만들어냈다. 문제가 완전히 사라진 건 설명문을 고쳤을 때가 아니라, 도구를 부르기 전에 프로그램이 입력값을 먼저 걸러냈을 때였다.

| 무엇을 했나 | 문제 건수 |
|---|---|
| 설명문에 아무 말 없음 | 3건 |
| 설명문에 "오류가 나면 되물어라" 적기 | 2건 |
| 설명문에 "추측 금지" 적기 | 1건 |
| **도구 부르기 전에 프로그램이 먼저 검사** | **0건** |

기록 원문은 [my-agent/traces/trace-02.txt](my-agent/traces/trace-02.txt)와 [trace-03.txt](my-agent/traces/trace-03.txt)에 있다.

그래서 이번 설계에서는 **몇 번 다시 시도할지, 언제 답을 멈출지를 오류마다 숫자로 못 박았다.** "적당히 다시 시도"라고 적으면 같은 걸 몇 번이고 다시 부르게 된다. 오류 14가지 중 열 가지는 다시 시도하지 않고 바로 멈춘다. 다시 시도하는 네 가지도, 사용자에게 물어서 내용이 달라진 뒤에만 다시 부른다.

그리고 규칙을 지키게 만드는 자리를 지시문이 아니라 **프로그램이 걸러내는 지점**에 뒀다. 지시문에도 같은 말을 쓰지만 그건 두 번째 방어선이다.

## 실행하지 않은 것과 이유

이번엔 문서만 만들었고 챗봇은 만들지 않았다. 그중에서도 특히 미뤄 둔 것들이다.

**물건을 지우는 도구를 만들지 않았다.** 지우면 되돌릴 수 없고, 앱 화면에는 이미 확인 단계가 있다. 챗봇에게 지우는 능력을 주면 그 확인 단계를 건너뛰는 길이 하나 더 생긴다. 대신 "전부 지워줘" 같은 요청이 왔을 때 어떻게 거절할지는 문서에 적어 뒀다.

**바꾸겠다는 제안을 실제 실행까지 연결하지 않았다.** 사람이 확인하는 순서를 문서로 못 박기 전에 연결해 버리면, 확인 없이 실행되는 길이 먼저 생긴다. 순서가 정해진 다음에 붙일 일이다.

**사용법 문서를 챗봇이 찾아볼 수 있게 정리해 두는 작업을 아직 하지 않았다.** 앞선 실습에서 문서를 저장하는 도중 원래 문장이 바뀌어 버린 일이 있었다. 96자짜리 문장이 208자로 늘고, 원문에 없던 말("다른 창고는 접근 권한이 없다")이 끼어들었다. 그리고 그 말이 검색을 거쳐 사용자에게 가는 최종 답까지 올라왔다. 기록은 [my-agent/traces/trace-mcp-01.txt](my-agent/traces/trace-mcp-01.txt)에 있다. 그래서 **원래 문장이 그대로 들어갔는지 보는 확인**을 먼저 만든 뒤에 정리 작업을 붙인다.

**지시문에 아직 비워 둔 칸이 넷 있다.** 확인이 몇 분 동안 유효한지, 없는 기능을 요청받았을 때 받아 적을지, 근거 문서끼리 어긋나면 어느 쪽이 맞는지, 답변 길이를 얼마로 제한할지. 넷 다 실제로 돌려 보지 않고는 정할 수 없는 것이라 비운 채로 두고 이유를 적었다. 사례 없이 정하면 지어낸 규칙이 된다.

## 다음에 측정할 지점

**오류 없이 지나가는 틀린 답이 몇 건 나오는지.** 시험 문항 3번과 4번이 이걸 노린다. 허용된 값 목록에는 들어 있어서 검사는 통과하지만 뜻은 어긋나는 경우다. 앞선 실습에서 "대전 물류센터 A-17"이라고 말한 것이 부산 창고 코드로, 물건 이름까지 다른 값으로 바뀌어 들어갔는데도 오류가 나지 않았다. 네 가지 요청 중 세 가지가 이렇게 조용히 지나갔다. 오류가 난 건 사용자가 허용되지 않은 코드를 직접 말한 한 가지뿐이었다. 오류가 났으면 고칠 수 있지만, 조용히 지나간 건 아무도 모른다.

**규칙을 우회하려는 요청이 지시문만으로 막히는지.** 시험 문항 8번이다. 지시문만으로 막혔다면 그건 운이 좋았던 것일 수 있다. 프로그램이 먼저 걸러내는 지점이 정말 필요한지 여기서 확인한다.

**문서를 정리해 저장할 때 문장 길이가 얼마나 변하는지.** 위의 96자→208자가 다시 나오는지 본다. 길이가 변했으면 내용도 변했다는 신호다.

**앞선 실습의 채점 기준에 남겨 둔 빈 칸.** "같은 값으로 세 번 연속 실패해도 통과로 본다"는 기준이 그대로 남아 있다. 돌려 본 뒤에 기준을 고치면 마음에 드는 결과를 통과로 만들게 되니, 그때는 고치지 않고 뒀다. 이번에 고칠 자리다.
