# trace-mcp-01 — 남이 만든 MCP 도구를 붙여 관찰
# 기록 시각 : 2026-08-27 15:09:49 +0900
# MCP 서버  : mcp-server-qdrant 1.29.1  (uvx mcp-server-qdrant, 프로토콜 2024-11-05)
# 저장소    : QDRANT_URL=":memory:"  QDRANT_COLLECTION="policies"
# 임베딩    : EMBEDDER_PROVIDER=fastembed  FASTEMBED_MODEL=BAAI/bge-small-en-v1.5 (로컬, API 키 없음)
# 모델      : qwen3.5:2b, 온도 0, reasoning=False   (실습 1·2 와 동일)
# 실행 명령 : uv run python mcp_probe.py --both  /  uv run python mcp_agent.py
# 로그      : runs/mcp_tools.json, runs/mcp_agent.json
# ⚠️ 인메모리이므로 서버 프로세스가 닫히면 저장이 사라진다. 이 파일이 유일한 기록이다.

## 관찰 1 — 도구 정의가 두 에이전트에 동일하게 주입되는가

두 설정 파일의 키 표기는 다르다:
  Claude Code (.mcp.json)      mcpServers / command + args / env
  opencode (opencode.json)     mcp / type="local" / command[] / environment

같은 실행 지점으로 모인다:
  Claude   : uvx mcp-server-qdrant
  opencode : uvx mcp-server-qdrant
  환경 변수 4개 완전 동일

각 설정으로 서버를 따로 띄워 tools/list 를 받은 결과:
  Claude Code 도구 : ['qdrant-find', 'qdrant-store']
  opencode 도구    : ['qdrant-find', 'qdrant-store']
  이름 집합 동일   : True
  qdrant-find      설명 동일 True   스키마 동일 True
  qdrant-store     설명 동일 True   스키마 동일 True

→ 키 이름만 다르고, 모델 컨텍스트에 들어가는 도구 정의는 바이트 단위로 같다.

주입되는 도구 정의 원문:
  qdrant-find   설명: "Look up memories in Qdrant. Use this tool when you need to:
                       - Find memories by their content
                       - Access memories for further analysis
                       - Get some personal information about the user"
                인자: query*(string), collection_name*(string)
  qdrant-store  설명: "Keep the memory for later use, when you are asked to remember something."
                인자: information*(string), collection_name*(string), metadata(선택)

## 관찰 2 — 같은 질문에 모델이 어떤 도구를 골랐는가

MCP 도구를 로컬 qwen3.5:2b 에 bind_tools 로 붙여 [1][2][3] 로 관찰했다.

1단계 저장 — 요청 3건 모두 모델이 스스로 qdrant_store 를 골랐다
  [1] qdrant_store  인자 {"information": ..., "collection_name": "policies"}
  [2] MCP 서버 응답 "Remembered: ... in collection policies"

2단계 검색
  요청: Search collection "policies" and answer: Which warehouses are approved for inventory lookups?
  [1] 모델이 고른 도구: qdrant_find
      인자: {"query": "approved warehouses for inventory lookup", "collection_name": "policies"}
      → 사용자 문장을 그대로 넣지 않고 검색어로 다시 썼다
  [2] MCP 서버 실행 결과 (의미 검색 3건, 관련도 순):
      1순위 <entry><content>Inventory lookups are read-only operations. Access is restricted
             to only the Seoul (SEOUL-01) and Busan (BUSAN-02) warehouse systems. ...</content>
      2순위 <entry><content>Warehouse codes must never be guessed from region names. ...</content>
      3순위 <entry><content>Refund requests over 100,000 KRW require manager approval ...</content>
  [3] 결과를 읽은 최종 답:
      "Based on my search of the policies regarding inventory lookups:
       * Access: Inventory queries are read-only and can only be performed using data from
         Seoul (SEOUL-01) or Busan (BUSAN-02). Other warehouses do not have access permissions.
       * Warehouse Codes: Warehouse codes must never be guessed based on region names;
         you should always ask the customer for their exact code to ensure accuracy"

→ 도구 선택·검색·인용이 모두 작동했다. 자기 함수(lab2_trace.py)와 구조가 완전히 같다:
  [1] 모델이 요청 → [2] 하네스가 실행(MCP 서버에 위임) → [3] 모델이 결과를 읽는다.

## ⚠️ 관찰 3 — 저장 단계에서 원문이 변형되었다 (예상하지 못한 발견)

하네스가 준 문장과 모델이 실제로 qdrant-store 에 보낸 문장을 대조했다. 3건 중 2건 변형.

[store 1] ⚠️ 96자 → 208자
  원문: "Inventory lookups are read-only. Only SEOUL-01 and BUSAN-02 warehouses are
         approved for queries."
  저장: "Inventory lookups are read-only operations. Access is restricted to only the
         Seoul (SEOUL-01) and Busan (BUSAN-02) warehouse systems. All other warehouses
         do not have access permissions for inventory queries."
  원문에 없던 단어: access, have, operations, other, permissions, restricted, systems, warehouse
  → "All other warehouses do not have access permissions" 는 원문에 없는 문장이다.

[store 2] ✅ 동일 (76자)
  "Refund requests over 100,000 KRW require manager approval before processing."

[store 3] ⚠️ 93자 → 110자
  원문: "... Ask the customer for the exact code."
  저장: "... Always ask the customer for the exact warehouse code."
  원문에 없던 단어: always

왜 문제인가 —
  RAG 는 "원문을 근거로 답한다" 는 전제로 쓴다. 그런데 저장 단계에서 모델이 문장을
  다시 쓰면, 나중에 검색해 인용하는 것은 원문이 아니라 모델이 각색한 문장이다.
  [2] 의 검색 결과가 정확해 보이고 [3] 의 답도 그럴듯하지만, 근거 자체가 이미 오염됐다.
  실제로 [3] 의 "Other warehouses do not have access permissions" 는 원문에 없던
  주장이 저장 단계에서 들어와 검색을 거쳐 최종 답까지 올라온 것이다.

  실습 2 전반부의 '조용한 정규화'(부산 3번 → BUSAN-02)와 같은 현상이다.
  모델은 도구 인자를 그대로 옮기지 않고 자기 말로 바꾼다.
  처방도 같다 — 저장은 모델에 맡기지 말고, 하네스가 원문을 직접 qdrant-store 에 넣는다.
  검색(qdrant-find)만 모델이 고르게 한다.

## 관찰 4 — 인메모리의 수명
서버 프로세스를 terminate 하면 저장한 3개 문장은 사라진다.
같은 프로세스 안에서 store → find 를 해야 한다. 다음 실행은 처음부터 다시 저장해야 한다.
그래서 이 파일이 유일한 근거 기록이다.
